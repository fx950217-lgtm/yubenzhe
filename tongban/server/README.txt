同伴 · 平台托管零钱与红包账本原型

新的产品边界
链上钱包：用户自行保管密钥，BSC 转账需用户签名并链上确认。
零钱余额：平台托管资产对应的内部记账余额。红包冻结、领取、到期退回发生在该账本。
本原型没有充值、提现、托管私钥、HTTP 接口、登录认证或真实资产。
网页聊天与红包当前仍是演示，不与本账本连接；演示数字不能兑换、提现或证明资产。

实现范围
Node 24 内置 node:sqlite，WAL、FULL 同步、外键、BEGIN IMMEDIATE 写事务。
采用复式记账：用户零钱和红包冻结账户都是正常贷方账户；内部转移记一借一贷。
所有账面余额均为非负整数文本，运算使用 BigInt。单个红包金额上限 10^30 最小单位。
无浮点金额。当前账本仅表示一种固定资产与精度；调用前必须统一资产单位。
资金操作失败时余额、凭证、领取记录和幂等响应一起回滚。
每个业务操作需幂等键，同一用户键不能换参数或改作其他操作。
重复同键领取返回原回执；同一用户换键再次领取失败；重复退款不会再次转账。

红包规则
ordinary：一个明确接收人，一个红包。
group_equal：成员快照最多 100 人，份数不超过名单人数，固定等额；总额须能整除份数。
group_random：同样的资格快照与份数上限。创建时以密码学随机源预分配所有金额；
使用二倍均值上限抽样，每份至少 1 最小单位、所有份额之和严格等于总额。
符合快照资格的用户先到先领取下一份；每人最多一份，不能变更接收人。
发送者可在群成员快照内领取自己发出的群红包一次；普通红包不能指定本人。
创建成功立即将总额从发送者可用余额划入专用冻结账户。
创建后恰好 24 小时到期，到期边界禁止领取；未领余额只能回到原发送者。
全部已领取的红包一直保留 fully_claimed 状态，不进入到期退款扫描；直接申请退款报 PACKET_FULLY_CLAIMED。
refundDue() 是到期工作器入口。生产环境必须接入持续运行的调度器；本目录没有安装后台任务。
成员快照由可信服务端从好友/群关系生成；本模块本身不能证明传入成员属于同一群。
退出群/后续加群不会改变已经创建的快照。冻结金额仍属于原发送者待分配款。
随机分配明细只存数据库，不在公开回执中返回。数据库管理员仍能看到它。

API（只供可信服务端调用）
import { CustodyLedger } from './server/custody-ledger.mjs';
const ledger = new CustodyLedger({ filename: '/persistent/path/ledger.sqlite' });
ledger.createAccount('alice');   // 余额始终从 0 开始，不产生资金
ledger.getBalance('alice');     // { userId, available, frozen }，金额是十进制字符串
ledger.createPacket({ senderId:'alice', type:'ordinary', recipientIds:['bob'],
  total:'100', maxClaims:1, idempotencyKey:'request-unique-key' });
ledger.claim({ packetId, userId:'bob', idempotencyKey:'claim-unique-key' });
ledger.getPacket(packetId);
ledger.refundExpired({ packetId, idempotencyKey:'refund-unique-key' });
ledger.refundDue({ limit:100 });
ledger.close();
调用者不能直接信任浏览器传入的 senderId、userId、recipientIds；必须从已验证身份和社交权限导出。
接口没有公开充值、测试加钱或改余额方法；零余额实例不能发红包。
测试夹具直接写独立临时数据库建立假资金及平衡凭证，不进入产品代码。

运行验证
Node 24 或兼容且提供 node:sqlite 的运行时：
node --test tests/custody-ledger.test.mjs
测试使用临时磁盘 SQLite，验证复式平衡、整数精度、失败回滚、重复请求、
普通/群等额/拼手气、24 小时边界退款及多个工作线程争抢最后一份。
本地 SQLite 测试不能替代财务审计、真实链路验证或生产安全审查。

上线所缺环节
1. 持久数据库部署、迁移、备份恢复与账本核对。生产多实例应使用支持行锁和明确隔离级别的
   数据库事务实现；SQLite 仅适合此单机验证，不能直接替代高并发多节点资金系统。
2. 充值必须验证 BSC 链、资产合约、充值地址和已达确认阈值的交易/事件；以链 ID、交易哈希、
   日志序号等唯一标识幂等入账。处理重组、重复通知、错误链/资产，不以客户端声明入账。
3. 提现须先冻结额度，建立不可重复支付的出款任务，对链上确认/失败/未知状态逐笔对账。
   状态不确定时禁止盲目重发或把冻结余额立即恢复，避免链上已付而账内重复可花。
4. 平台托管地址的密钥管理与用户自托管钱包分离；需要受控签名、最小权限、审批和审计，
   生产资金密钥不得放进浏览器、源码、日志、SQLite 或普通环境变量。
5. 身份认证、成员权限、风控限额、完整凭证核对、异常监控与退款调度器；不能由客户端自报余额。
6. 明确平台托管的运营责任、资产及精度、充值/提现政策、余额与链上储备核对流程。
未完成这些环节前不得接收或托管真实用户资金。
