# 一台电脑 + 一台手机 跑通方案（可直接交给 Codex 开发）

日期：2026-10-11
目标：**在最小范围内跑通「手机聊天窗口 → 驱动电脑上的 AI → 结果回传手机」**
前置文档：`AI-CHAT-HUB-20261011.md`（方向与架构分析）

---

## 零、方案总览（先看懂这 5 行）

```
① 手机 App（现有 tongban 网页）
      ↓  发一条消息（走你已有的服务器）
② 你的服务器（现有 yubenzhe-deploy）
      ↓  转发给"桥"
③ 桥程序（新写，跑在电脑上，主动向外连，不开入站端口）
      ↓  在本机执行
④ Codex CLI（本机已装 v0.153.4）
      ↓  返回结果
⑤ 原路返回 → 手机看到回复
```

**核心原则（不可妥协）**：
- **桥主动连服务器，服务器绝不主动连用户电脑**（不开放任何入站端口）
- **服务器只转发消息文本，不接触文件、不需要 AI Key**
- **桥开源可审计**

**为什么这版能跑通**：不碰云机、不碰支付、不碰多 AI 讨论。**只做单机单 Agent 的最小闭环。**

## 二、阶段划分（三个阶段，每阶段独立可验收）

### 阶段 A：局域网跑通（**建议先做这个，最快看到结果**）

**目标**：手机连同一个 WiFi，打开网页，发消息，电脑上的 Codex 干活，结果显示在手机上。

**为什么先做局域网**：不用服务器、不用域名、不用 HTTPS、不用打洞。**半小时能见效。**

### 阶段 B：走公网服务器

**目标**：手机用 4G/5G 也能用。

**改什么**：把桥的连接目标从"局域网电脑 IP"改成"你的服务器"，服务器转发。

### 阶段 C：接进现有聊天界面

**目标**：不是独立页面，而是在现有的「消息」Tab 里，能选到一个"我的电脑"联系人。

## 三、阶段 A 详细方案（给 Codex 的实现规格）

### 3.1 新增一个文件：`tools/local-bridge/bridge.mjs`

**职责**：跑在电脑上，开一个 HTTP 服务，收到请求就调用本机 Codex，返回结果。

**技术要求**：

1. **只监听局域网**，不要监听 `0.0.0.0` 以外的地址（绑 `0.0.0.0` 是为了手机能连，但必须带配对码校验）
2. **必须有配对码机制**（否则同一 WiFi 下任何人都能用你的 Codex）
3. **必须限制可执行目录**（不能让手机端随意指定任意路径）
4. **必须有超时**（Codex 可能跑很久，设 5 分钟上限）
5. **输出要流式回传**（不能等全部跑完才返回，否则手机端像卡死）

**接口设计（最小）**：

```
POST /pair/verify
  body: { code: "6位数字" }
  → { ok: true, deviceName: "我的电脑", token: "<长期token>" }

GET  /health
  → { ok: true, device: "PC-20260624ZQQP", codex: "0.153.4" }

POST /task              （需要 Bearer token）
  headers: Authorization: Bearer <token>
  body: { prompt: "帮我把这段文字翻译成英文", cwd: "D:/work" }
  → SSE 流式返回:
      {"type":"start","taskId":"..."}
      {"type":"chunk","text":"..."}
      {"type":"done","exitCode":0,"durationMs":12345}
      {"type":"error","message":"..."}
```

**启动方式**：

```bash
node tools/local-bridge/bridge.mjs --port 18930 --cwd "C:/Users/Administrator/Documents/Codex/2026-10-09/git-2/work/yubenzhe"
```

终端会打印：

```
==================================================
  愚笨者 · 本地桥已启动
--------------------------------------------------
  配对码： 4 8 2 9 1 3      （6 位，每次启动随机）
  局域网地址：http://192.168.1.11:18930
  允许执行目录：C:/Users/.../yubenzhe
  提示：手机连同一个 WiFi，打开上面的地址
==================================================
```

### 3.2 Codex 调用方式（关键实现细节）

**已验证可用的调用**：

```js
import { spawn } from 'node:child_process';

const CODEX = 'C:/Users/Administrator/.codex/.sandbox-bin/codex.exe';

// 非交互式执行（headless）
const child = spawn(CODEX, ['exec', '--json', prompt], {
  cwd: allowedCwd,
  env: process.env,
  stdio: ['ignore', 'pipe', 'pipe']
});
```

> ⚠️ **Codex 必须先自己确认 `codex exec` 的确切参数**（`codex exec --help`）。
> 我实测到了 `codex.exe --version` 返回 `codex-cli 0.153.4`，
> 但 `exec` 子命令的具体参数（是否支持 `--json`、如何指定 cwd、如何流式输出）
> **必须让 Codex 自己跑 `--help` 确认，不要猜。**

**如果 `codex exec` 不好用**，降级方案：
用 `codex-command-runner-0.153.4.exe`（同目录下，8MB 那个，看起来就是给程序化调用用的）。
**两个都试，用能跑通的那个。**

### 3.3 新增一个页面给手机用：`tools/local-bridge/mobile.html`

**极简单文件**（不要接进主项目，先跑通再说）：

- 打开时要求**输入配对码**
- 一个输入框 + 一个发送按钮
- 下面是一个消息列表（用户消息 / AI 回复区分颜色）
- 支持流式显示（AI 一边说一边显示）
- 顶部显示连接状态：`● 已连接 我的电脑` / `○ 未连接`

**技术要求**：
- 原生 HTML + JS，**不引入任何框架**（和项目现有风格一致）
- `fetch` + `ReadableStream` 读 SSE
- 配对 token 存 `localStorage`

### 3.4 安全要求（这一版最简单，但底线必须有）

| 要求 | 为什么 |
|---|---|
| **配对码 6 位随机，每次启动变化** | 防止同 WiFi 的陌生人直接用你的 Codex |
| **配对后发长期 token，存 localStorage** | 不用每次都输 |
| **限制可执行目录**（启动参数指定，不可由请求改） | 防止手机端 `cwd: "C:/"` 乱搞 |
| **task 请求要有大小上限**（prompt ≤ 4000 字符） | 防滥用 |
| **单次超时 5 分钟** | Codex 可能挂住 |
| **并发上限 1**（同时只跑一个任务） | 防止你电脑被跑满 |
| **日志不记录 prompt 全文**（只记长度和 taskId） | 隐私 |

## 四、阶段 B 详细方案（走公网，改哪些）

**在阶段 A 跑通后再做。改动很小**：

1. **桥的连接方向翻转**：从"监听端口"改成"主动连接服务器 + 长轮询/WebSocket"
2. **服务器新增转发端点**（放在 `yubenzhe-deploy/server/` 下）：
   - `POST /api/bridge/register` —— 桥上线时注册
   - `GET /api/bridge/poll` —— 桥轮询取任务
   - `POST /api/bridge/result` —— 桥回传结果
3. **配对码改为在手机 App 里生成**，电脑上输手机上的码（或反过来）

> ⚠️ **这一阶段的坑**：桥断了要能自动重连（用户会关机、会断网）。
> 手机端要能明确显示"设备离线"，不能一直转圈。

## 九、风险与限制（诚实说明）

| 风险 | 说明 |
|---|---|
| **电脑必须开着** | 桥跑在你电脑上，关机 = AI 下线。这是设计如此，不是 bug |
| **Codex 可能不适合所有任务** | 它是编码 Agent，做文件/代码类任务强，做纯聊天不一定比云端模型好 |
| **同一 WiFi 才安全** | 局域网版本不要暴露到公网（没有 TLS，配对码也挡不住暴力破解） |
| **Codex 有成本** | 你用的是自己的 Codex 额度，跑太多会消耗 |
| **并发只能 1** | 一个任务跑的时候，手机再发要排队（刻意设计，防止电脑被跑满） |

## 十、为什么先做这个（战略理由）

这件事同时验证了**三个核心假设**，而且是**一次验证**：

| 假设 | 怎么被验证 |
|---|---|
| 「手机控制电脑」有人要吗？ | 你自己会不会用第 4 次 |
| 技术路径通不通？ | 桥能不能真的驱动 Codex |
| 这个入口对不对？ | 用起来顺不顺，比五个 Tab 是否更自然 |

**而且它不依赖任何外部方**：不用买服务商、不用牌照、不用等审核、不用改架构。

**从今天到跑通，只需要 Codex 写三个文件。**
