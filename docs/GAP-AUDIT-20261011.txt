零、审计先说结论
================================================================

这个项目不是「PPT 项目」。它有三个真实的基础：
  1) 代码真实存在，且测试真的能跑通（我本机实跑，非引用文档数字）
  2) 合规红线是真的硬编码进了代码，不是只写在文档里
  3) 账务、幂等、状态机这些「最容易出事」的地方，写得比多数创业项目扎实

但这不意味着可以上线。阻挡上线的**不是代码质量，是三个还没接通的外部依赖
（真实邮件 / 真实收款 / 商店发布）和三个还没做的安全动作（合约审计 / 真机验收 / 主网）**。

一句话：**工程已经走到「能演示、能给内测用户用」，但离「能对外收钱运营」还差最后一公里，
而这一公里恰好全在「钱、账号、法务」上，不在功能上。**

二、代码质量：哪些地方其实做得很好（不必再改）
================================================================

为避免误伤，先说清楚哪些是**已经达标、不建议再动**的：

1) **积分账务（points-service.mjs）——这是全项目最扎实的模块。**
   - 用 BigInt 整数记账，字符串存库，**没有浮点误差**
   - 复式记账：每笔记账 entries 求和必须为 0，不为 0 直接抛错（`Unbalanced points journal`）
   - SAVEPOINT 原子性，出错 ROLLBACK
   - requestId + payload 哈希做幂等，同 ID 改内容返回 409
   - 明确禁止的原因清单（transfer/withdrawal/gas-exchange/asset-exchange/deposit/purchase/recruitment/investment-return）
   - 欢迎分只能 1000、只能一次（硬编码校验）
   → **这个模块可以直接拿给专业账务人员看，不会丢人。**

2) **合规红线是「代码级」硬约束，不是文档里的口号。**
   - `handle()` 里任何非 GET 的 points 请求**一律 403** (`POINTS_NONTRANSFERABLE`)，转赠/提现在协议层就不存在
   - 收益暗示类文案被 ALLOWED/FORBIDDEN 双清单挡住
   - 旧平台资产接口返回 410，迁移 015 带 SHA-256 归档校验
   → 这正是 V0.2 想做的事，**做到了**。

3) **AI 供应商层的安全约束写得很专业。**
   - host 硬编码白名单（api.openai.com），密码/用户名出现在 URL 直接报错
   - `redirect:'error'` 不跟随跳转（防 SSRF 重定向）
   - 用户输入永远拼在 `user` 角色，**不能注入进 system instructions**
   - 响应体有大小上限，超限 abort
   - 明确写「不要索取助记词、私钥、密码」
   → 比市面上大量 AI 套壳项目的实现水平高。

4) **工作台状态机 + 预算不变量。**
   - 步骤消费只在 running 状态
   - 失败全额释放、取消按已完成步骤核销
   - `Budget invariant violated` / `Reservation invariant violated` 双保险
   - 受限账号的任务会被 tick 主动结算（不会悬空占额度）
   - 报价 60 秒过期、审批卡带 version 与 expires_at
   → 资金相关的边界处理是认真的。

5) **CI 是可复现的。**
   GitHub Actions 用 commit SHA 锁定 action（不是 @v4 浮动标签），
   版本三处一致性校验（tongban / admin / deploy 必须同版本），
   产出带 SHA256SUMS 的可下载工件，且明确标注 `deployed: false`。
   → 有工程纪律。

6) **钱包的密钥边界是对的。**
   - 只开放 BSC 测试网（chainId 97），**代码里没有主网开关**（注释明写 "There is no mainnet toggle."）
   - keystore 版本/链 ID/地址三重校验，读坏就提示「保留原始数据、用助记词恢复」
   - 5 分钟自动锁定 + 2 分钟预览窗口
   - 密钥与产品账号密码**分离**
   → 自托管的核心安全边界成立。

三、真正的缺口（按「距离上线多远」排序）
================================================================

### 缺口 A：真实邮件发不出去 —— 阻断注册与找回，P0

**证据**：`server/account-mail.mjs` 全文只有三种适配器：
   - `createDisabledMailAdapter`（默认，直接抛错）
   - `createSimulationMailAdapter`（仅 loopback）
   - `createInternalPreviewMailAdapter`（仅 HTTPS 内测域）

文件末尾注释直接写着：
> "A production provider and OTP HMAC secret must be explicitly injected; no network is used by default."

**含义**：现在所有验证码都是「模拟」的，只在已通过门禁的页面显示。
**真实用户根本没收到过邮件。** 而邮箱验证是注册和找回账号的必经环节。

**要补什么**：
   1) 接一个真实投递服务商（SendGrid / 阿里云邮件推送 / AWS SES 皆可）
   2) 实现 `{mode:'provider', send({to,kind,code,expiresAt,locale})}` 接口
   3) 配置并发/频率限制、退信处理、发信域名 SPF/DKIM/DMARC
   4) 注入 `EMAIL_OTP_SECRET`（≥32 字符，代码已强制校验）

**这不是代码难度问题，是「开通服务 + 配置域名」的运营动作。**


### 缺口 B：没有收款能力 —— 无法产生收入，P0（商业上的唯一前提）

**证据**：全仓库搜 `stripe|payment|checkout|billing|subscription`，
命中的全是「通知/审批」相关词，**没有任何一个支付网关集成**。
`workbench-service.mjs` 的 invoice 表里 `userChargeMicro` 恒为 `'0'`，
`payer` 是 `'local-points'` 或 `'platform-trial'`。

**含义**：
   - 用户拿到的 1000 积分是「白送」的本地欢迎分
   - **没有充值入口，没有付费路径，平台目前收不到一分钱**
   - `planGoal` 里的「预算」是积分预算，不是真钱

**要补什么**：
   1) 选支付渠道（考虑你的现状：如果面向全球，Stripe / Paddle / Lemon Squeezy；
      如果是越南本地，VNPay / MoMo）
   2) 定「积分 ↔ 真钱」的兑换定价模型（这是商业模式的核心决策，不是技术问题）
   3) 做充值的订单/回调/对账闭环（这块要非常小心，涉及退款与拒付）
   4) ⚠️ **注意合规**：一旦平台卖出积分再让用户消费，性质可能从「工具」滑向
      「预付卡/代币」，这与你的合规团队之前定的「工具提供者」定位有张力。
      **建议充值定价前一定要拿到律师意见。**


### 缺口 C：合约没审计、区块浏览器没验证 —— 但幸好只开了测试网，P0→P1

**证据**：
   - `contracts/package.json` 描述里自己写着 `"unaudited"`
   - 文档明确：`区块浏览器源码验证尚未提交`，只有 standard JSON
   - SingleDistribution 的「选择性中止边界未解决」，随机模式未开启

**含义**：合约能跑、测试网 7 笔交易金额守恒，但**没有第三方安全审计**。
好消息是：**代码里没有主网开关**，且 `Gas 代付、积分兑资产、营销发币默认关闭`，
所以当前风险被控制在测试网内，**不构成即时资金风险**。

**要补什么**：
   1) 正式开启主网前，必须做独立合约审计（这是硬门槛）
   2) 提交区块浏览器源码验证（提升透明度，成本很低，建议尽早做）
   3) 明确 SingleDistribution 的去留（要么补完边界，要么归档）


### 缺口 D：iOS 完全停在上一个版本 —— 三端不一致，P1

**证据**：`yubenzhe-ios/ios-build-status.json`：
```
"version": "0.13.0", "build": 16,
"deviceVerified": false, "installedOnDevice": true,
"jailbreak": "Dopamine", "layout": "Dopamine rootless"
```
文档也多次声明 `iOS 本轮未更新`。

**含义**：
   - iOS 的包是 0.13.0，落后当前 0.14.0-dev.7 **整整一个版本**
   - 它是**越狱环境（Dopamine）下的 ad-hoc 签名**，不是 App Store 包
   - `deviceVerified: false` —— 真机验证未完成

**要补什么**：
   1) iOS 同步到 dev.7（有 CI workflow `ios-preview.yml`，需要 Mac runner）
   2) 真机完整验收
   3) App Store 上架的**必备材料**：开发者账号、隐私清单、App Review 说明、
      以及最关键的——**自托管钱包类 App 的 Apple 审核风险预案**
      （Apple 对「钱包+加密货币」审核严格，需提前准备合规说明）


### 缺口 E：真机与完整 UI 验收未做 —— 声明与实际的最大落差，P1

**证据（文档自述，我认为这个自述是诚实的）**：
   - `完整登录后UI与实体设备专项未全部验收`
   - `Windows 尚无发布者代码签名`
   - Android 只在**模拟器**上验证（`安卓模拟器完成覆盖升级`）
   - 100 轮用户旅程是 `300 个合成账号、2504 次真实HTTP`，
     文档自己强调 `不是100名真人`

**含义**：这是**内测版**，不是可发布会。缺少：
   1) Windows 代码签名证书（否则用户看到「未知发布者」警告，严重影响信任）
   2) Android 实体设备（至少主流机型）装机验收
   3) 真实用户（哪怕是 20 个朋友）的完整走查
   4) 弱网、应用升级、前后台切换等真机才暴露的问题


### 缺口 F：MANIFEST 基线过期 —— 完整性保险失效，P2（但很好修）

**证据**：MANIFEST.json version 0.9.0，实跑 127 项文件与快照不一致。
（详见第一节「偏差 2」）

**含义**：这道防线本来是防「文件被偷换 / 混入私密文件」的，
现在因为清单是旧版本的，**在交接模式下会直接判 failed**，
换句话说：**这个检查目前无法通过，也就无法发挥它应有的保护作用。**

**要补什么**：用当前 dev.7 源码重新生成 MANIFEST 基线（并保留旧基线做历史对照）。
这是个低成本、高价值的收尾动作。**建议优先做，因为它影响所有后续交接的可信度。**


### 缺口 G：一处死代码 —— 不影响运行，但会误导审计，P2

**证据**：`scripts/simulate-group-gifts-100.mjs` 仍 `import` 已被移除的
`yubenzhe-deploy/server/platform-assets.mjs`。
现有审计文档也承认它「明确失效」，「已移除的平台托管账务」。

**含义**：跑不起来，不是当前构建入口。但**它会让外部审计者误以为项目还在做平台托管红包**，
而这是你已经明确退役的高危业务。属于「历史残留造成认知风险」。

**要补什么**：移到 `archive/` 目录或加明显的 `.deprecated` 标记（不要直接删，保留审计痕迹）。

四、还有几个「文档没提，但我认为你应该知道」的点
================================================================

1) **后端整体只有 1873 行。** 这不是缺点，恰恰是优点——代码量小意味着可审计性强。
   但也要意识到：**当前实现的是「本地规则式」能力**，不是通用 AI 代理。
   `workbench-service.mjs` 里的 planner 是 `'local-rules'`，executor 是 `'local-file-parser'`，
   capabilities 接口自己诚实标注：
   `'本地规则式计划与文件工具；未连接语言模型、云桌面或真实支付。'`
   → 宣传时**不要**把它说成「通用 AI 能帮你自动干活」，那会踩虚假宣传。

2) **AI 目前只有两个入口，且一个是 0.6b 小模型。**
   服务器跑的是 `qwen3:0.6b`（6 亿参数，极小）。它能证明「链路通」，
   但**质量撑不起「AI 工作台」的品牌承诺**。这是产品体验上的真实短板，
   比代码问题更影响用户留存。

3) **云电脑（云机）是空的。** `capabilities.desktop.available = false`，
   原因写死：`'尚未配置真实云桌面服务商'`。UI 上有入口，点进去明确不可用。
   → 这是「诚实但未完成」，符合你的「不假成功」原则，但**它是产品故事里的重要一环，缺了会显得产品单薄。**

4) **推送（Web Push）代码在，但真实投递未验收。** 
   文档明确：不能以「service worker 文件存在」推断完成。这个自述是准确的。

5) **i18n 未接入运行链。** `tongban/src/i18n.js` 有独立测试，但**不在 app.js 导入链里**。
   而你的目标是「全球」市场，**中英双语界面是刚需，现在是断的。**

   **本轮追加验证（比文档更严格）**：我实际 grep 了整个 `tongban/src/`，
   `import ... from './i18n'` 的命中数为 **0** —— 也就是说 i18n.js（54 行）
   **没有任何一个模块引用它**，是完全悬空的死代码。
   文档的措辞是「未进入当前 app.js 运行导入链」，实际情况比这更彻底：
   它不是「接了但没启用」，而是**根本没接线**。
   → 面向全球市场，这是必须补的基础设施，且工作量不大（54 行的模块已有，缺接入）。

五、优先级建议（如果只能做三件事）
================================================================

**第一梯队（决定能不能收钱）**
   1. 接真实邮件服务商 —— 否则用户注册不了
   2. 定价 + 接支付网关 + 拿律师意见 —— 否则商业模式不成立
   3. 重新生成 MANIFEST 基线 —— 否则所有交接证据不可信

**第二梯队（决定能不能发布）**
   4. Windows 代码签名证书
   5. Android 实体机 + iOS 同步 dev.7
   6. 区块浏览器源码验证（成本低、收益高，建议插队做）

**第三梯队（决定能不能留客）**
   7. 换一个真正能用的模型（0.6b → 有实用价值的模型）
   8. 中英双语接通（目标全球，这是刚需）
   9. 云电脑服务商选型（或者从产品故事里暂时摘掉）

**关于合约审计**：在你决定开主网之前，它不是当前最紧急的事
（因为主网开关根本没做）。但**一旦决定开主网，它是不可绕过的第一道门**。
