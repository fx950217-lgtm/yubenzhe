第二部分：数据模型（新增 1 个迁移 017）
-----------------------------------------------------------

新建 `yubenzhe-deploy/migrations/017-moment-artifacts.sql`。

核心原则：**不要新建一套「成果分享表」**，而是给已有的 `moments` 表加一个可选引用。

```sql
-- 给朋友圈动态加一个可选的成果引用。NULL 表示普通动态。
ALTER TABLE moments ADD COLUMN workbench_file_id TEXT REFERENCES workbench_files(id);
ALTER TABLE moments ADD COLUMN share_snapshot TEXT;

CREATE INDEX moments_workbench_file ON moments(workbench_file_id);
```

字段说明（写进代码注释）：

1. `workbench_file_id`
   - 指向 `workbench_files.id`，只允许指向 `kind='output'` 的成果
   - **可空**：普通朋友圈动态这里为 NULL，不影响现有功能
   - **不加 ON DELETE CASCADE**：成果过期清理后，动态本身要保留（见下面的快照）

2. `share_snapshot`（JSON 字符串，可空）
   - 快照内容：`{fileName, size, sha256, mime, taskTitle, operation, createdAt}`
   - **为什么要快照**：成果文件只保留 30 天。30 天后文件没了，
     但动态要还在、要能显示「这是一个什么成果」。所以发布时把元信息固化下来。
   - **快照里绝对不能放文件内容**（BLOB），只放元信息。

3. **不要**新增任何「下载他人成果」的权限表或接口。分享是「给你看这个成果长什么样」，
   **不是「给你下载文件」**。这一点是整个设计的核心边界，见第四部分。

迁移必须符合项目现有的迁移规范（版本号、checksum、`social_migrations` 表）。
参考 016 的写法和 015 的注释风格。

第三部分：后端接口
-----------------------------------------------------------

3.1 修改 `POST /moments`（在 social-moments.mjs 里）

在现有发布流程上增加两个**可选**字段：`workbenchFileId`（可选）。

规则：
- `fields()` 白名单要加上 `workbenchFileId`
- 如果传了 `workbenchFileId`：
  - 必须是 UUID 格式，否则 400 `INVALID_ARTIFACT`
  - 必须存在、必须属于当前用户、必须是 `kind='output'`、必须未过期
    否则 404 `ARTIFACT_NOT_FOUND`（不要区分「不存在」和「不是你的」，避免信息泄露）
  - 读取该文件的元信息，写入 `share_snapshot`
- 如果没传：行为完全不变，`workbench_file_id` 为 NULL
- **digest 计算要包含 `workbenchFileId`**，否则幂等校验会漏
- **不要求**有成果才能发动态；也不要求**必须**带成果 —— 两种动态共存

3.2 修改 `GET /moments` 返回

每条动态的返回里新增：
```
artifact: row.workbench_file_id ? {
  fileId: row.workbench_file_id,
  fileName, size, sha256, mime, taskTitle, operation, createdAt   // 来自 share_snapshot
  available: <boolean>   // 文件当前是否还在（未过期且存在）
} : null
```
- `available` 需要实时查 `workbench_files` 判断（是否过期）
- **`available=false` 时，界面显示「文件已过期」，但动态和快照信息照常显示**
- **绝对不要返回文件内容**

3.3 ⭐ 关键边界：不做「下载别人的成果」

**明确禁止**新增以下任何接口：
- ❌ `GET /moments/:id/artifact`（下载动态里的成果）
- ❌ 任何让非所有者取到别人成果文件内容的路径
- ❌ 任何时候放宽 `workbench/files/:id` 的 owner 校验

原因（写进代码注释，这是设计意图）：
> 成果文件可能含用户的敏感数据。分享是「展示」，不是「分发」。
> 想看内容 → 让作者自己决定要不要另外发给你。
> 这条边界守住，才不会让「分享」变成「数据泄露通道」。

如果将来要开放下载，必须是**作者显式勾选**的独立功能，不能在本次实现。

3.4 成果过期与动态的关系

- 成果文件 30 天过期被清理时，**不要删除动态**
- 动态保留，`available` 自动变成 `false`
- 不需要为这个场景写额外的清理任务 —— `available` 是查询时算的，不是存下来的
