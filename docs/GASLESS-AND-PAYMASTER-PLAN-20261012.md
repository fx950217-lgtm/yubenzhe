# Gas 代付方案（合约能不能解决 gas 费）

日期：2026-10-12
问题来源：**「钱包+社交的产品 有没有合约的方式，解决 gas 费的」**

---

## 第零节 · 直接回答（先看这三句）

**1. 能。合约层面有成熟方案，已经生产运行三年了。**
你现在需要的不是「发明方案」，是「接入一个已有标准」。这个标准叫 **ERC-4337（账户抽象）**。

**2. 但「解决 gas 费」的正确理解是：gas 不是被消灭了，是被转移了。**
gas 是付给区块链矿工/验证者的**真金白银**，谁都免不了。合约能做的只有一件事：
**把「谁掏这笔钱」从用户改成了平台。**

所以「免 gas」这个词是营销说法，技术上是 **「平台代付 gas」**。

**3. 这跟你「平台无任何收费项目」的方针不冲突，但会产生持续支出。**
- ✅ 不冲突：你不收用户一分钱 ≠ 你不能替用户花钱。**零收费管的是「收入」，代付管的是「支出」。**
- ⚠️ 但这是**每天都在烧的现金支出**，金额随用户量线性增长。**这个必须你自己点头。**

第 36 行，原文：

> 没有管理员、升级、平台提款、提前撤销、改接收人、**代付**或积分兑换入口。

**这三句话已经把答案说得清清楚楚了：现在没有，要做就得新建。**

## 第四节 · 如果走 ERC-4337，具体要改什么（工作清单）

### 4.1 ⚠️ 合约层：两个必须先解决的问题

**问题 1：`chainId != 97` 硬限制（多链必须改）**

```solidity
// contracts/src/EqualDistribution.sol 第 55 行
if (block.chainid != 97 || ...) revert InvalidConfig();

// contracts/src/InternalTestToken.sol 第 10 行
if (block.chainid != 97) revert TestnetOnly();
```

**这两行是写死的测试网锁。** 你要「多链都要支持」→ **必须改成构造参数白名单**（例如 `mapping(uint256 => bool) public allowedChain`），而不是删掉了事。

**改法建议**：构造函数接受 `allowedChainIds` 参数，部署时按目标链传入。保留测试网的 97，主网按需加 56/1/137/42161。

⚠️ **`SingleDistribution.sol` 第 114 行没有链锁但已把 `block.chainid` 编进签名域** —— 这是**正确的**（防跨链重放），**不要动它**。

**问题 2：`claim()` 的强校验要重新审视**

```solidity
// EqualDistribution.sol 第 94 行
if (p.account != msg.sender) revert Unauthorized();

// SingleDistribution.sol 第 166 行 / 221 行
if (p.account != msg.sender) revert Unauthorized();
```

**走 ERC-4337 时这条一般不用改** —— 因为智能账户自己就是 `msg.sender`，`p.account` 存的也是这个智能账户地址，校验依然成立。✅

**但走 ERC-2771 时这条必须改成 `_msgSender()`** —— 否则转发器提交时 `msg.sender` 是转发器地址，校验直接失败，用户永远领不到。❌

**这是路线选择的直接后果，也是为什么推荐 A 的原因之一。**

### 4.2 钱包层：从 EOA 迁到智能账户

| 现状 | 改造后 |
|---|---|
| `wallet.js` L10：`chainId:97, symbol:'tBNB'` | 多链网络表（56/1/137/42161 + 保留 97） |
| L50/62：vault 读写绑死 `chainId:97` | ⚠️ **这是设计缺陷**，改为按链分别存储 |
| L247：`if(BigInt(chain)!==97n)` 拒绝 | 改为链白名单校验 |
| L282-299：自己估 gas、自己付 | 改为：估 gas → 取 Paymaster stub → 再估 → 取 Paymaster 签名 → 提交给 Bundler |
| **L512：`signTransaction({type:0})`** | 改为签 `UserOperation`（**不是普通交易**） |
| L298/L483：`BALANCE_INSUFFICIENT` 报错 | **代付成功后这条不应该再出现** |

**新的调用流程（MegaFuel 官方流程）：**

```
1. 构建 UserOperation
2. pm_getPaymasterStubData      → 拿到占位 paymaster 数据
3. eth_estimateUserOperationGas → 估算真实 gas
4. pm_getPaymasterData          → 触发政策校验，拿到最终签名（同时冻结预算）
5. eth_sendUserOperation        → 提交给 Bundler
6. eth_getUserOperationReceipt  → 轮询回执（不要当成即时确认）
```

### 4.3 后端层：新增「代付政策服务」

需要新建（对应你现在 `yubenzhe-deploy/server/` 的 40 个 `.mjs` 风格）：

- `paymaster-service.mjs` —— 封装 MegaFuel 政策 API（申请/查询/停用/余额）
- `sponsorship-policy.mjs` —— 什么动作允许代付（白名单：合约地址 + 方法选择器 + 单笔上限）
- `sponsorship-accounting.mjs` —— 逐笔记账，**对标 MegaFuel 的 `sponsoredGasfee`/`remainingBalance`**
- 监控告警 —— **70% / 90% 预算阈值告警**（这是必须的，不是可选的）

### 4.4 新增测试

- 代付成功路径
- 政策拒绝路径（白名单外、超额）
- 预算耗尽降级路径（**必须优雅降级：告诉用户「本次需自付 gas」，而不是直接报错崩掉**）
- 跨链一致性（同地址在多链都能跑）

## 第五节 · ⚠️ 如果你也想做 ERC-2771（备选路线）

**这条路线不推荐作为主路线**，但如果你将来想让「用户不换地址也能免 gas」，它有用。**8 条安全标准，一条都不能少：**

1. **每笔 meta transaction 必须有 nonce 跟踪**（链上验证，防重放）
2. **EIP-712 domain separator 必须含 `chainId`**（防跨链重放）
3. **可信转发器地址必须在部署时不可变设定**，无管理员覆盖能力（否则管理员=上帝模式）
4. **接收合约里所有 `msg.sender` 必须审计并替换为 `_msgSender()`**
   → **你的合约有 22 处，全部要过一遍**（见 1.3 节）
5. **签名过期时间戳必须由合约强制**（建议有效期 **5–60 分钟**）
6. **Relayer API 必须做速率限制**（按钱包地址 / IP / 总量三重限）
7. **必须做专门的 relay 安全审计**（通用审计会漏掉 relay 特有攻击面）
8. **Gas 预算必须监控**，70% / 90% 消耗阈值告警

**另外两条工程纪律：**
- 提交前**必须模拟交易**（`eth_call` 预演）
- gas limit 加 **20–30% padding**

## 第六节 · 风控与成本（钱要花多少，怎么防被刷爆）

### 6.1 成本模型

**gas 不是被消灭，是被你付了。** 参考量级：

| 链 | 一次转账/领取的典型 gas 成本 | 备注 |
|---|---|---|
| BSC | 约 **$0.01–0.05** | 最便宜，适合大规模红包 |
| Polygon | 约 **$0.01–0.10** | 便宜 |
| Arbitrum | 约 **$0.05–0.30** | 中等 |
| Ethereum 主网 | 约 **$0.5–5** | ⚠️ **贵到不适合代付红包** |

**估算示例**：假设日活 1000 人，每人每天领 1 次红包，全部走 BSC 代付：
`1000 × $0.03 = $30/天 ≈ $900/月`

**这个数字随用户量线性增长。** 你必须先定一个**月度赞助预算上限**，超了就自动降级。

### 6.2 必须做的防刷（否则会被刷爆）

ERC-4337 的 paymaster 是**攻击者的明确目标**，官方审计指南列了三类攻击：

| 攻击类型 | 怎么发生 | 你的防线 |
|---|---|---|
| **耗尽攻击（Depletion）** | 攻击者狂发「能通过校验但啥也不干」的 UserOp，把你的 deposit 抽干 | ✅ **白名单 sender**（MegaFuel 支持）<br>✅ **按用户/小时限速**<br>✅ **每用户每日上限** |
| **postOp 记账操纵** | 用闪电贷在「校验」和「执行」之间移动代币价格，少付 gas | ✅ **价格在校验时锁定并带到 postOp**（不用现货价）<br>✅ 我们不收用户 gas，天然规避大半 |
| **postOp 耗尽 gas** | 恶意 UserOp 吃光 gas，让 postOp 没 gas 记账 | ✅ **postOp 记账路径必须 gas-bounded**<br>✅ 失败时转入内部记账而不是 revert |

### 6.3 政策要像「风险限额」来写，不是像「功能开关」

这是从业者反复强调的一条原则（**直接照抄进你的政策设计**）：

1. **先设一个极小的单笔上限** —— 这是最快限制单次损失的办法
2. **硬白名单**（收款地址 / 合约 / 方法选择器）—— **不在白名单里就根本不该能碰**
3. **有效期要短** —— 密钥泄露时，短效期能限制损失
4. **加一个会话总预算** —— 防止「多次小额」慢慢放血
5. **撤销要做成一等公民** —— 随时能一键关停赞助

**MegaFuel 官方也强调：「政策限额不替代你自己的风控。」**

## 第八节 · ⚠️ 合规联动（这跟你的上架计划有关）

**好消息：零收费方针在这里帮了两次忙。**

1. **Apple 3.1.1** 管的是「用加密货币/钱包**解锁功能**绕过内购」。
   你平台**零收费 + 代付 gas** = **没有东西要解锁，也没有东西要买** → 这条天然规避。✅

2. **代付 gas 不收用户钱** → **不构成「交易所」或「支付服务」**（没有用户资金流转）。
   这比「用户充值买 gas」安全得多。✅

**⚠️ 但红线在这里：**

- **绝对不要把 gas 代付包装成可交易的东西**（比如「gas 卡」「gas 额度」）
  → 那会变成 **Apple 3.1.1 里的 "license keys"**，直接踩线。
- **绝对不要做「邀请返利送 gas」「完成任务送 gas」**
  → 这是 **Apple 3.1.5(v) 明令禁止的「invite rebate / task reward for crypto」**。
- **赞助预算是平台自己的营销支出，不是任何形式的「用户资产」。**
  → 记账上必须清楚：这是你的成本科目，不是用户的余额。

**一句话：代付是「你替用户付账」，绝不能变成「你给用户发钱」。** 前者是客服体验，后者是发币。
