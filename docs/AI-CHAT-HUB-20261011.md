## 一、你说的这件事，叫什么（对齐概念）

### 1.1 你的描述翻译成技术语言

| 你的原话 | 技术说法 |
|---|---|
| 我下载了 codex，通过信息和他对话 | **本地 CLI Agent 的手机遥控（Remote Control）** |
| 下载了 work（我），通过他和你对话 | 同上，只是换了一个 Agent |
| 把所有 AI 拉到一群区讨论问题 | **多 Agent 群聊（Multi-Agent Group Chat）** |
| 这样才会爆发思维风暴和灵感 | **多视角对抗式推理（Multi-perspective debate）** |

### 1.2 ⚠️ 一个必须分清的区别

**「在群里 @ 一个 AI」** 和 **「在群里拉进 Codex 本体」** 是**两件完全不同的事**：

| | 云端 AI 群聊 | 你电脑上的 Codex |
|---|---|---|
| 例子 | 群里 @DeepSeek、@GPT | 群里 @我的Codex |
| 跑在哪 | 服务器 | **你自己家的电脑** |
| 能干什么 | 只能聊天 | **能读你的文件、改你的代码、跑命令** |
| 需不需要装东西 | 不需要 | **需要你电脑上开着 Codex** |
| 断电了怎么办 | 没事 | **AI 就下线了** |

**你说的那个「爆发思维风暴」的版本，是第二种，也是更值钱的那个。**

## 二、这个方向已经被官方验证了（重要）

### 2.1 Anthropic 在 2026-03-20 发布了 Channels

原文事实（dev.to / VentureBeat 报道）：

- **2026-03-20**，Anthropic 发布 **Claude Code Channels**（研究预览）
- 用法：**从 Telegram 或 Discord 发一条消息**，你本机的 Claude Code 会话执行任务，**用同一个聊天软件回复你**
- 架构叫 **"push, not pull"**：不是你去轮询，而是**外部事件主动推给正在运行的 Agent**
- **关键安全设计**：**本机不开放任何入站端口**，是**你的机器主动向外连接**（轮询 Bot API）

> 用户原话复述的场景（来自报道）：
> 「我在**地铁上**推送了一次生产提交。不是用笔记本，不是 SSH。
> 我从手机发了一条 Telegram 消息，坐在我桌上的 Claude Code 接住它，修好了 bug，回复了 diff。」

### 2.2 更早的官方动作

| 时间 | 产品 | 能力 |
|---|---|---|
| 2026-02 | **Claude Remote Control** | 用 iPhone 远程操作 Mac；终端显示二维码，手机扫码接管会话 |
| 2026-03-20 | **Claude Code Channels** | 从 Telegram / Discord 驱动本机 Agent |

**Remote Control 的关键细节（对你极有参考价值）**：
- 终端里跑 `claude remote-control` → 显示**会话 URL + 二维码**（空格键切换）
- 手机扫码即接管，**两端实时同步**
- **不是投屏、不是远程桌面** —— Claude 始终跑在你本机，能访问完整的文件系统和 MCP 服务器
- **手机只是一个窗口**
- ⚠️ 限制：**关掉终端会话就结束**（不是守护进程）；**网络断超约 10 分钟会超时**

### 2.3 还有个开源参照：OpenClaw

报道提到 **OpenClaw 拿了 20 万 GitHub star**，做的事就是：
**把 WhatsApp、iMessage、Telegram 接到开发者的 AI 上**。

> 有意思的是：**你本机就装了 `openclaw`**（在 `%APPDATA%\npm\` 下）。
> 这说明这条路已经有人在走，而且是被人用真金白银的 star 投票的。

### 2.4 这意味着什么

**巨头刚把它做成了一等公民功能**，这是"方向确定"的最强信号。
但同时也意味着：**你要做的不是"发明这个功能"，而是"把它做进熟人圈子和钱包里"。**

## 三、⚠️ 必须先解决的悖论（这是核心）

### 3.1 悖论长这样

你的产品卖点是 **「自托管、隐私、平台不碰你的东西」**。
但「让平台连到你家的电脑上跑 Codex」**天然和这个卖点冲突**。

用一个表说清楚：

| 如果你做… | 用户会问 | 后果 |
|---|---|---|
| 平台自己搭云机跑 AI | 「那我的文件上传给你们了？」 | **破坏"不碰数据"的承诺** |
| 让用户电脑开端口给平台连 | 「你们能进我家电脑？」 | **安全噩梦，没人敢装** |
| 让用户把 Codex 的 API Key 交给平台 | 「你们能花我的钱？」 | **信任崩塌** |

### 3.2 解法：**把角色倒过来 —— 不是平台连用户，是用户连自己**

这是我认为**唯一正确的架构**：

```
❌ 错误方向：平台 → 连用户的电脑（平台主动，用户被动）
✅ 正确方向：用户手机 → 连自己的电脑（用户主动，平台只当中转）
```

具体做法（借鉴 Anthropic 的 "push, not pull"）：

1. **用户在自己电脑上跑一个「桥」程序**（一个几十行的小工具，开源可审计）
2. 这个桥**主动向外连接**你的服务器（**不开放任何入站端口**）
3. 用户在手机 App 里发消息 → 服务器转发给桥 → 桥在本机启动 Codex/WorkBuddy → 结果回传手机
4. **全程：平台只转发消息，不接触文件内容，不需要 Key**

**这个设计的好处**：

| 问题 | 解法 |
|---|---|
| 平台会不会看我文件？ | 桥是本机进程，**平台只看到出入的消息文本** |
| 要不要开放端口？ | **不要**，是用户机器主动向外连 |
| 断电怎么办？ | 桥断线，手机端显示"设备离线"，**符合直觉** |
| 用户能不能审计？ | **桥开源**，用户自己看代码 |

> **类比**：这就像 **远程桌面 vs 远程代理**的区别。
> 你要做的是后者 —— 不是"看到你的屏幕"，而是"你告诉它要干什么，它在你的机器上干完"。

### 3.3 所以第一版该做什么

**不做**通用的"连所有 AI"。
**做**一件事：**让用户用自己的手机，驱动自己电脑上的一个 AI，并把结果分享给群里的朋友。**

## 四、功能拆解（按能不能落地排序）

### 4.1 🟢 第一版能做的（不依赖任何外部审批）

| 功能 | 说明 | 难度 |
|---|---|---|
| **手机 ↔ 本机 AI 单聊** | 群里/私聊里和一个本机 Agent 对话 | 中 |
| **会话二维码配对** | 电脑上显示码，手机扫一下就接管（学 Anthropic） | 低 |
| **设备列表 + 在线状态** | "我的电脑：在线/离线" | 低 |
| **群聊里 @ 一个本机 AI** | 群里拉一个 AI 进来回答问题 | 中 |
| **结果转发到群/朋友圈** | AI 干完的活，一键分享 | 低 |

### 4.2 🟡 第二版（多 AI 群聊 —— 你说的"爆发思维风暴"）

| 功能 | 说明 |
|---|---|
| **同群多 Agent** | 群里同时有 Codex、WorkBuddy、DeepSeek，各自发言 |
| **@ 指定 AI** | `@codex 帮我改这段代码` / `@work 帮我查资料` |
| **让 AI 互相看对方的话** | 这才是"思维风暴"的关键：**A 说完 B 能看到并反驳** |
| **话题触发** | 说一句"评估这个方案"，自动叫 3 个 AI 各出一版意见 |
| **汇总** | 把多个 AI 的意见合并成一张对比表 |

> ⚠️ **重要提醒**：真正的"思维风暴"**不是把 AI 拉进群就自动发生**。
> 它需要**结构**：谁先说、谁反驳、以什么标准收敛。
> 否则你只会得到**一堆互相点赞的 AI**（这在业界是个已知问题：模型之间倾向于互相认同）。

**所以第二版真正的难点不是"接进来"，是"怎么让它们真的互相质疑"。**

### 4.3 🔴 暂时不做的

| 不做 | 原因 |
|---|---|
| 平台托管用户的 AI Key | 信任崩塌 |
| 云端跑用户的 Codex | 破坏自托管承诺 |
| 付费 AI 自动兜底 | 成本失控（Agent 任务成本是对话的 8–15 倍） |
| 群里 AI 自动互相回复无限循环 | **会烧光你的 API 余额**，必须设轮次上限 |

## 六、一个必须提醒你的成本风险

**Agent 类任务的算力成本是普通对话的 8–15 倍**（Bernstein，2026-02）。

如果「多 AI 群聊」不设限制，会出现这种情况：

> 3 个 AI 在群里互相回复 → 每条消息都触发 3 次调用 → 循环 20 轮 → **60 次调用**
> 用户只说了「你们讨论一下」这一句话。

**必须一开始就定死**：
1. **单次讨论的轮次上限**（比如最多 6 轮）
2. **每个 AI 每天的消息配额**
3. **积分扣费前置**（发起讨论前先扣，不是事后算）
4. **兜底模型**（讨论用便宜的 `deepseek-v4-flash`，不用贵的）

你的 `points-service.mjs` 已经有"预留/核销/释放"的完整机制，**直接拿来当闸门就行**。

## 七、我的建议：这件事在路线图里排哪

### 7.1 它应该是 1.0 的一部分吗？

**一半是。** 拆开看：

| 子功能 | 放哪 | 理由 |
|---|---|---|
| 群里和**云端** AI 对话 | **1.0 做** | 成本低、复用现有群聊、不改架构 |
| 结果分享到群 | **1.0 做** | 本来就该做（P0） |
| 手机连**自己电脑上的** AI | **1.5 做** | 需要新写桥程序，是个独立工程 |
| 多 AI 同群讨论 | **2.0 做** | 需要先有 1.5 的设备和身份体系 |

### 7.2 为什么这个功能重要（放在全局看）

你之前的产品结构是「五个 Tab，每个 Tab 干一件事」。
但**「聊天窗口」其实是一个天然的统一入口**：

```
用户想在手机上说一句话
  ├─ 让 AI 帮我干活        → 走"本机 AI" →
  ├─ 叫朋友一起讨论        → 走"群聊"     →  全都是"发消息"
  ├─ 给朋友转钱            → 走"钱包"     →
  └─ 把结果存起来          → 走"朋友圈"   →
```

**发消息是人最自然的动作。** 把这四个能力都挂到"发消息"下面，
比让用户去记"这个功能在哪个 Tab 里"要顺得多。

> **这就是你说的"把懒做到极致"** —— 懒的本质不是功能少，是**用户不用想该去哪儿**。
