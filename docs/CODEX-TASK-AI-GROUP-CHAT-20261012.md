### 2.2 群聊基础设施（已有，可复用）

| 群组工作流 | `020-group-workflows.sql` | ✅ 参考现有群机制 |

### 2.3 🔴 发现的核心矛盾：AI 不是账号，进不了群

**这是本次最大的设计问题。**

```sql
-- messages 表（003-social.sql:14）
CREATE TABLE messages(
  ...
  sender TEXT NOT NULL REFERENCES accounts(id),   -- ⚠️ 外键强制必须是账号
  ...
);
```

**AI 没有 `accounts` 记录，所以：**
- ❌ 不能直接作为 `sender` 插入消息
- ❌ 不能直接进 `conversation_members`（那张表的 `account_id` 也是 `REFERENCES accounts(id)`）

**三条可选路线（在第三节详述）：**

| 路线 | 做法 | 评价 |
|---|---|---|
| **甲：AI 消息由「设备主人」代发** | AI 的回复以**你本人账号**发进群，但带 `provider` 标记 | ✅ **推荐**，改动最小，语义最干净 |
| **乙：给 AI 建影子账号** | 每个 AI 建一个特殊 accounts 记录 | ⚠️ 污染账号体系，且会误入好友/搜索 |
| **丙：改建 messages 表支持非账号 sender** | 加 `sender_kind` 列 | ⚠️ 动核心表，风险大，影响面广 |

**➡️ 强烈建议走「甲」。** 理由见第三节。

## 第三节 · 为什么用户的选择组合是安全的（好消息）

用户选了「**每轮都要你点一下才继续**」——**这一个选择直接消灭了最大的风险。**

### 多 AI 群聊的死循环风险

如果没有刹车：

```
你问一句
   ↓
A 回复 → B 看到 → B 回复 → C 看到 → C 回复 → A 看到 → A 又回复 → …
   ↓
  无限循环（业界称 "agent loop"），烧钱烧到天亮
```

**但用户选了「每轮手动点」→ 这个循环根本形不成。**

```
你问一句
   ↓
A、B、C 各回复一次（并发）
   ↓
停 ← 等你点「继续」才发下一轮
   ↓
你点 → 再跑一轮 → 停
```

**➡️ 你的手指就是刹车。这是最稳的设计。**

⚠️ **但仍然要有兜底**（见第六节红线 3）：
- 即使手动模式，也要有**轮数上限**（建议 10 轮）
- 要有**总时长上限**（防止用户忘了点）
- 要有**一键停全部**

## 第四节 · 架构设计

### 4.1 群里的 AI 怎么呈现

**走「甲」路线：AI 消息由设备主人代发，带 `provider` 标记。**

```
┌──────── 群聊「产品讨论」────────┐
│                                  │
│  你（我）                         │
│  ┌────────────────────────────┐ │
│  │ 帮我分析一下这个方案        │ │
│  └────────────────────────────┘ │
│                                  │
│  我 · Codex  【我的电脑】         │  ← 代发 + provider 标记
│  ┌────────────────────────────┐ │
│  │ 从工程角度，我建议…         │ │
│  └────────────────────────────┘ │
│                                  │
│  我 · Claude 【我的电脑】         │
│  ┌────────────────────────────┐ │
│  │ 我补充一点不同的看法…       │ │
│  └────────────────────────────┘ │
│                                  │
└──────────────────────────────────┘
```

**为什么这样最干净：**
- ✅ `messages.sender` 依然是你的账号 → **不用动核心表**
- ✅ 显示成「我 · Codex」→ 用户能分清是哪个 AI 说的
- ✅ **不会**污染好友列表、搜索、朋友圈
- ✅ 群成员表**不用改**（AI 不是成员，只是你的「发言工具」）

⚠️ **语义上要诚实**：UI 上要明确「这是你的电脑上的 Codex 代你发言」，**不能伪装成独立的人**。

### 4.2 并发怎么实现

**同一台电脑，多个 AI 并发跑：**

```
电脑端 codex-runner.mjs
    active=null          ← ❌ 现在：单个
         ↓ 改成
    active=new Map()     ← ✅ 改成：Map<taskId, job>
```

**并发上限必须设**（⚠️ 不能无限）：

| 限制 | 建议值 | 理由 |
|---|---|---|
| 单机并发任务数 | **3** | 一台电脑 CPU/内存有限，跑太多会卡死 |
| 上限可配置 | 是 | 不同机器配置不同 |

⚠️ **必须做资源保护**：
- 并发数达上限 → **排队**，不是报错（报错体验差）
- 要有**单机总内存/CPU 保护**（跑 3 个 AI 可能吃光内存）

### 4.3 服务端怎么做

**服务端也要从「单任务」改成「多任务」：**

| 位置 | 现在 | 改成 |
|---|---|---|
| `ai-channel.mjs:80` | `if(active)throw` | 支持多个同时 active |
| `ai-channel.mjs:84` | 单个 `active` 对象 | `Map<taskId, task>` |
| `ai-channel.mjs:113` | `events:current?current.events:[]` | 上报所有活跃任务的 events |

**⚠️ 这里的改造比电脑端更危险**，因为涉及：
- **事件序号（`seq`）** 的实现现在是全局递增，多任务要**按任务分别递增**
- **租约（lease）** 现在是单个 `leaseUntil`，多任务要**每个任务一个租约**
- **`ack` 机制** 现在是单个序号，多任务要**按任务 ack**

**这三处如果改错，会导致任务状态错乱、消息丢失或重复。**

## 第五节 · ⚠️ 新场景下的一个真实边界问题

用户说「可见性隔离不是问题」——**大部分情况下是对的，但有一个新问题必须解决：**

### 问题：AI 进群后，谁能看到 AI 的回复？

场景：你把 A 电脑的 Codex 拉进一个**有别人的群**（比如和朋友的群）。

```
你的电脑 Codex 在群里回复了
         ↓
群里所有人都看到了
         ↓
但他们看到的是「我 · Codex」
         ↓
问题是：这台电脑是你的私有设备，凭什么它的 AI 在公开群里发言？
```

**这不是安全漏洞，是「设备归属」的语义问题。**

**➡️ 建议规则（需要用户确认，见第八节）：**

| 群类型 | AI 可否发言 | 理由 |
|---|---|---|
| **只有你自己的群**（或你建的单人群） | ✅ 可以 | 完全私有 |
| **有好友的群** | ⚠️ **默认禁止**，需显式开启 | 你的私有设备不该自动在公开场合发言 |
| **工作群** | ⚠️ 同上 | 同上 |

**这个规则很重要，因为：**
- 你的电脑上有你的**文件、项目、凭据**
- AI 在群里发言 = 可能**泄露你电脑上的信息**
- 用户说「信息中转」→ 那**转给谁**必须由用户控制

## 第六节 · 红线（给 Codex 的硬约束）

1. ❌ **不得**让 AI 消息的 `sender` 伪造为他人（**必须是你自己的账号**）
2. ❌ **不得**给 AI 建 `accounts` 记录（不污染账号体系）
3. ❌ **不得**做「AI 之间无限自动对话」——**必须有轮数上限（建议 10 轮）**
4. ❌ **不得**在无上限情况下自动继续（即使手动模式也要有总时长兜底）
5. ❌ **不得**让单机并发无上限（**上限 3，可配置**）
6. ❌ **不得**让并发任务共用 `seq` / `leaseUntil` / `ack`（**必须按任务隔离**）
7. ❌ **不得**在有好友的群里默认允许 AI 发言（**默认禁止，需显式开**）
8. ❌ **不得**破坏现有「设备会话仅本人可见」
9. ❌ **不得**让 AI 群消息进入朋友圈/搜索/好友推荐
10. ✅ **必须**有「一键停全部 AI」的按钮
11. ✅ **必须**在并发达上限时**排队**而不是报错
12. ✅ **必须**有单机资源保护（内存/CPU）
13. ✅ **必须**在 UI 上明确区分「你本人说的」vs「你的电脑上的 AI 代说的」
14. ✅ **必须**保留现有单 AI 场景的全部行为不变（向后兼容）

## 第七节 · 分块任务

### 【A 块】电脑端：并发改造

- A1. `codex-runner.mjs`：`active=null` → `active=new Map()`
- A2. `codex-runner.mjs:117`：拆掉 `AI_BUSY` 单任务锁，改成**上限检查 + 排队**
- A3. `codex-runner.mjs:143`：`busy` 改成「是否达上限」
- A4. **资源保护**：并发达上限时的排队机制 + 内存/CPU 监控
- A5. 每个任务独立的 `taskId` 追踪，互不干扰

### 【B 块】服务端：多任务并发

- B1. `ai-channel.mjs:80`：拆掉「同时分配多个任务」的拒绝
- B2. `ai-channel.mjs:84`：`active` 单对象 → `Map<taskId, task>`
- B3. **`seq` 按任务独立递增**（⚠️ 这是最容易改错的地方）
- B4. **`leaseUntil` 按任务独立**（同理）
- B5. **`ack` 按任务独立**（同理）
- B6. `ai-channel.mjs:113`：上报所有活跃任务
- B7. 迁移 `025-ai-group-chat.sql`（⚠️ 编号见第九节）
  - `messages` 表加 `provider` 列（标出是哪个 AI 说的）
  - `messages` 表加 `device_id` 列（标出来自哪台电脑）
  - 群设置加 `allow_device_ai` 列（控制是否允许 AI 在群里发言）

### 【C 块】手机端：AI 群聊界面

- C1. 建群时可选「把哪台电脑的哪些 AI 拉进来」
- C2. 群消息里 AI 的回复要显示「我 · Codex · 我的电脑」
- C3. **「继续下一轮」按钮**（用户手动点的那个刹车）
- C4. **「一键停全部」按钮**
- C5. 轮数计数器显示（「第 2 / 10 轮」）
- C6. 群设置里「允许设备 AI 发言」开关（**默认关**）

### 【D 块】防循环兜底

- D1. 轮数上限（默认 10，可配）
- D2. 总时长上限（建议 30 分钟，超时自动停）
- D3. 相同内容重复检测（如果 AI 在重复说同一句话，自动停）
- D4. 用户离开页面/断网 → 自动停
